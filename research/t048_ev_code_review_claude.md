## Методологические замечания (не блокеры, но обязательны к раскрытию)
**M1 (важно). h2h vs base — самый благоприятный соперник для sale_beam, и points-критерий там малоинформативен.**
base vs base — точное зеркало: мировая маржа ровно 0 (кроме seat-асимметрии, напр. 93048506 ±601, 93048504 ±1,
которые гасятся усреднением по местам). Сценарий веса 0.5 «соперник = наша очередь» здесь **буквально истинен**,
поэтому sale_beam берёт детерминированные +$20–35/мир и почти каждую ничью превращает в победу → `points ≥ .65`
выполняется от любого крошечного zero-sum преимущества. Информативна только маржа; перенос на ладдер зависит от
того, продают ли реальные соперники те же товары в тех же индексах слотов. Решающая часть — sanity tetsu/ozer44
(8 миров, конечная панель; README это признаёт). Рекомендация: в README кандидата писать эффект как «$/мир vs
зеркало» + sanity-Δ, не как win-rate.

**M2. late_ev инертен.** Во всех 24 h2h-играх late_ev: `added=held=released=changed=0`; маржа по мирам = 0
(ненулевые ±601/±1 — seat-эффект базы). Пороги (`mean > max(8, 2%)`, `min(deltas) ≥ 0`, ≥16 валидных
flow-точек из 24) при зеркальном сопернике не срабатывают. Код безопасен, но h2h-гейт для late_ev не может
пройти (points=0.5) и упаковывать его нечего. Не подбирать пороги на gate-мирах.

**M3. Хвост маржи sale_beam — траекторные каскады, а не прямой эффект.** 93048513: +$1944 при
`expected_gain`=145; 93048507: +125 при 111. Бутстрап по 16 мирам будет доминироваться 1–2 такими мирами.
Рекомендую дополнительно показать медиану мировой маржи и сумму `expected_gain` (прямой механический эффект),
чтобы CI не читался как «надёжные +$X».

## Мелкие находки в коде (некритично)
- **L1 (late_ev hold).** `q = min(8, orders[i][2], sold[it])` уменьшает количество ордера, а не фактическую
  продажу: если последний SELL-ордер товара превышает остаток склада (BC часто заказывает «с запасом»),
  уменьшение на q не сокращает реальную продажу, но `pending` и `stats['held']` всё равно выставляются, а
  release на следующем ходу продаст ещё q единиц. Корректнее `q = min(8, sold_in_this_slot)`, где
  `sold_in_this_slot` — фактическое исполнение именно последнего слота. Сейчас не влияет (M2).
- **L2 (late_ev add).** «now»-цена считает только свои продажи (`inv += sold`), а rival-flow текущего хода
  (который исполняется до/в lockstep с нашими хвостовыми ордерами) попадает только в «later»-ветку →
  систематический оптимистичный сдвиг в пользу немедленной продажи на ~1 ход flow. Сейчас инертно.
- **L3 (sale_beam).** Скорер оценивает только маржу денег за текущий ход; это корректно лишь потому, что
  итоговый инвентарь инвариантен к перестановке (п.5). Если в будущем разрешат менять количества — нужен
  терминальный/value-член. Штраф 0.25/перемещение и порог +2 разумны.
- **L4.** sale_beam переставляет и WHEAT/FERTILIZER SELL в суффиксе (README упоминает запрет только для
  late_ev). Легально (после последней траты), просто отметить.
